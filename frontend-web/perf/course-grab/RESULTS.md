# 抢课压测结果

环境：本地单机（JMeter 5.6.3，后端 `127.0.0.1:8080`，开课班 509，容量 80，抢课前人数 0）。

## 1. 多人抢课（`course-grab-stress.jmx`，500 线程，每线程一个学生）

运行时间：2026-10-14 20:49（最近一次有效运行）

| 结果 | 次数 |
| --- | --- |
| HTTP 200，`code:0`，选课成功 | 80 |
| HTTP 500，"名额已满" | 420 |
| HTTP 401 | 0 |
| HTTP 500，"您已选过该课程" | 0 |

断言：抢课前 `enrolled_count=0`，抢课后 `enrolled_count=80`，预期新增 80，实际新增 80。**通过**，没有超卖，人数增量与成功次数一致。

说明：更早的一次运行出现过 75 个 401 和 80 个"您已选过该课程"，原因分别是登录账号数据不全和选课记录残留，重置数据并补齐账号后两类错误都消失。

## 2. 同一学生重复抢课（`course-same-user-stress.jmx`，50 线程，同一账号 `stress001`）

运行时间：2026-10-15 12:19

| 结果 | 次数 |
| --- | --- |
| HTTP 200，`code:0`，选课成功 | 1 |
| HTTP 500，"您已选过该课程" | 49 |

断言：抢课前 `enrolled_count=0`，抢课后 `enrolled_count=1`，成功次数 1。**通过**，同一学生只成功一次，人数增量与成功次数一致。

## 结论

- 容量 80、500 人同时抢：不超卖，成功 80 人，其余被满员拒绝。
- 同一学生 50 线程同时抢：只成功一次，其余被"已选过"拒绝。服务端在并发下能正确去重。

## 已知问题与待确认

- 接口文档写的是 HTTP 202 异步受理，实际同步返回 HTTP 200 + `code:0`；满员是 HTTP 500 + `code:500`，文档写的是 409 + `40900`。需要和后端确认口径。
- 只跑了单次，没有重复取样，结果代表单次运行，不是稳定统计值。
- 这些是读写混合的业务压测，不是吞吐能力测试。服务的并发吞吐（只读接口约 30 req/s，见之前的摸底结果）单独记录，不在本文件内。
